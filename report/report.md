# NOVA: an explainable, workload-aware search over GCC optimization flags — evaluation report

This report is generated by `scripts/make_report.py` from saved raw measurements under `benchmarks/results/`. Every
measured value in it is a placeholder filled from those files; `report/traceability.json` lists, for each value, the
source files and the formula. Nothing here is an illustrative number. The report describes **one machine, one compiler and
three small kernels**; it makes no claim about other setups and no claim that NOVA replaces or improves on GCC in general.

## 1. Research question and hypotheses

**Question.** Under the same candidate-evaluation budget, does a search over a small whitelist of GCC flag
configurations that uses workload descriptors, earlier experiments and its own earlier outcomes (the *adaptive* policy)
choose faster configurations than random search, and does the choice still help on input sizes it never tuned on?

| id | hypothesis |
|---|---|
| H1 | adaptive beats random at equal budget on the tuning sizes |
| H2 | the advantage carries over to unseen (holdout) input sizes |
| H3 | the workload-descriptor signal helps (adaptive vs adaptive without features) |
| H4 | the prior-experiment (history) signal helps |
| H5 | the within-run feedback signal helps |

H3, H4 and H5 are each evaluated on holdout and, with the suffix `t`, on tuning sizes. Verdicts are produced by a fixed
rule (section 9.3) from the saved data, not by judgement.

## 2. Problem framing: what sources establish and what is our inference

- GCC documents that optimization flags have workload-dependent effects ("may or may not make it run faster" for loop
  unrolling) and that the set enabled at each `-O` level depends on target and configuration [R1]. This establishes that
  the choice of flags is a legitimate tuning dimension; it does not establish that tuning pays off for any particular program.
- Automated program autotuning with search over configurations is prior art [R2]. NOVA's search is a small, transparent
  heuristic, not a re-implementation of that system, and NOVA does not claim novelty for flag autotuning itself.
- Measurement practice (repeat runs, validate outputs, report medians, interleave to reduce drift) is taken from
  Google Benchmark's documentation of random interleaving [R4] and SPEC's run rules [R5]. NOVA follows those *ideas*; its
  benchmarks are not SPEC-conformant.
- **Our inference, not established by any source:** that workload descriptors, history and feedback can steer the search
  better than random sampling in this setting. That is exactly what H1 to H5 test.
- These sources do not establish how often developers struggle with flag selection; this report makes no prevalence claim.

## 3. System architecture and responsibility boundary

NOVA has two independent tracks. First, an educational compiler for a tiny integer language (lexer, parser, AST, semantic
analysis, three-address code, a four-pass optimizer, reference interpreters) that is tested separately and plays no role in
the measurements below. Second, **SmartPass**, an experiment controller: it asks **GCC** to compile fixed C++ kernels with
whitelisted flag sets, runs the binaries, checks their output against an independent oracle and records timings. GCC does
all code generation and optimization; NOVA only chooses which flags to try, in which order, and measures the result.

## 4. Candidate space and budget accounting

The searchable space has 22 configurations (opt level `-O2`/`-O3` combined with `-funroll-loops`,
`-ftree-vectorize`, `-fprefetch-loop-arrays`, `-march=native`, canonicalized and de-duplicated), plus the two baselines
`-O2` and `-O3`: 24 configurations in total. Only whitelisted flags can reach the compiler; fast-math
flags are excluded. The budget B counts searched candidates that are built and validated; the two baselines are always
evaluated in addition and never counted, the same convention for every method; there are no retries. Wall-clock cost
(including pilot measurements of the adaptive method) is reported separately in section 8.4.

## 5. Environment

Operating system Windows 11 Home 26H2 (build 26300); CPU Intel(R) Core(TM) Ultra 7 155H with 22 logical CPUs; 15789 MiB of
RAM; compiler `g++ (MinGW.org GCC-6.3.0-1) 6.3.0` with target `mingw32`. All timed runs were pinned to one logical CPU
(affinity mask 0x10) with raised priority, because unpinned timing on this hybrid-core CPU was visibly noisier
(see the V0.6 baseline experiments). The compiler is old and targets the older thirty-two bit x86 architecture; modern GCC versions may behave differently.

## 6. Correctness validation and its limits

Every candidate is run once before it may be timed, and every later run is checked again. A run passes if five statistics
of the output array (sum, three sample elements, weighted sum) and the sizes match an independent long-double reference
within a relative tolerance of 1e-09. A candidate that ever fails is recorded with its reason and can never be
ranked. In the exhaustive tables, 0 of 288 records failed build or correctness. Limits: the
oracle checks statistics, not every output element; strict floating-point flags were used throughout (no `-ffast-math`);
the test suite includes a deliberately incorrect kernel that the oracle rejects.

## 7. Timing protocol

Each sample is the kernel's own timer for the compute region of a fresh process. Each configuration gets
2 discarded warm-up runs after a discarded validation run and then 15 timed runs, executed in
interleaved rounds in a seeded random order. All raw samples are stored; medians and interquartile ranges (IQR) are reported.
Across the 12 measured workloads the median relative IQR of the two baselines was 2.1 percent and the
maximum 7.2 percent; differences smaller than that noise are treated as inconclusive throughout.

### 9.3 Decision rule and how to read it

A budget counts as *positive* for a hypothesis if the bootstrap interval is entirely above zero **and** the mean difference is
positive in at least two thirds of the workloads; *negative* in the mirror-image case. A hypothesis is SUPPORTED if at least
three quarters of the evaluated budgets are positive and none is negative, NOT SUPPORTED in the mirror-image case, and
INCONCLUSIVE otherwise (including "no difference at all"). The seeds of one workload are not independent evidence about other
workloads, so these verdicts hold **for these workloads only**; with three kernels and a finite space nothing here
generalizes to arbitrary programs. A verdict of SUPPORTED means the measured difference is consistent across seeds and workloads
here; it is not a statement about effect size, which the mean differences in 9.1 show to be small and to shrink as the budget grows.

## 10. Failures, regressions and threats to validity

- **Priors are not independent of the data.** The workload-descriptor prior constants were written before the study but
  after the author had looked at earlier timings of the same kernels (docs/adaptive.md). H3 therefore partly measures
  how well the author guessed, not an independent discovery.
- **Replay re-uses measurements.** Methods differ only in which saved samples they see; real searches would re-measure with fresh noise.
  The real runs in 8.4 are too few to confirm or refute the replay.
- **Tiny space and few workloads.** With 22 searchable configurations a small budget already covers a large part of the space, and
  all methods are exhaustive at the top budget. Six tuning workloads from three kernels cannot represent real programs.
- **One machine and compiler.** Results depend on this CPU, on pinning to one logical CPU (which changes absolute times and
  memory behaviour) and on an old thirty-two bit GCC.
- **Correctness oracle is statistical.** See section 6.
- **Selected-slower regressions** are listed in 8.3; they occur mainly for methods that evaluate very few candidates.
- **Noise.** Differences below the noise level (section 7) are inconclusive; the report uses medians, never minima.

## 11. Limitations and what the data do not show

NOVA's search results are not evidence that the educational compiler is useful for GCC tuning (they are independent tracks);
they do not show speedups on unseen programs; `-Ofast`/fast-math was measured separately in V0.6 and is excluded from the
space; the POSIX process runner has not been run in this environment.

## 12. Reproduction

On a machine with CMake, a C++ compiler with C++ standard seventeen (the results above used GCC from MinGW) and Python:

```
cmake -S . -B build && cmake --build build
ctest --test-dir build --output-on-failure
for k in stencil vector_add matmul; do
  build/nova table $k --role=all --reps=15 --warmup=2 --affinity=10 --high-priority --id=V0.8-table-$k
done
build/nova study --tables=benchmarks/results/V0.8-table-stencil,benchmarks/results/V0.8-table-vector_add,benchmarks/results/V0.8-table-matmul \
  --out=benchmarks/results/V0.8-study --seeds=30 \
  --methods=fixed,random,adaptive,adaptive-no-features,adaptive-no-history,adaptive-no-feedback,baseline-O2,baseline-O3
python scripts/make_report.py
```

The study and the report are deterministic functions of the saved tables; re-measuring the tables on another machine will give
different numbers. The affinity mask in the command assumes a fifth logical CPU exists; choose any single CPU. The real runs of section 8.4 are produced by
`scripts/run_real_experiments.sh`. Regenerating only the report from the saved data needs no compiler: `python scripts/make_report.py`.
