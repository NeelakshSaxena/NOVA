## Slide 2: Problem statement

1. Which flags?

- -O2 and -O3 are only two of many GCC optimization flags.
- Their effect depends on the program; for loop unrolling the manual says it “may or may not make it run faster” [1].
- Every candidate costs one compile and one run to test.

2. Still correct?

- A faster binary is useless if its answer changes.
- -Ofast enables transformations “not valid for all standard-compliant programs” [1].
- So each candidate must be checked against a reference.

3. Speedup real?

- Run times vary: on our machine the baseline spread (IQR) reached about 7% pinned and about 25% unpinned.
- So we need repeated runs, medians and saved raw samples [3, 4].
- A choice tuned on one input size may not hold on others.

Scope of NOVA: three small numerical C++ kernels (matmul, vector_add, stencil) and GCC flags only. It does not claim that every developer has this problem; no survey was done.

**Sources:** docs/01-product-requirements.md; docs/08-references.md; state/KNOWN_ISSUES.md (N-004); report/report.md section 7

**Speaker notes:**

> In everyday language: GCC can make a program faster, but picking the right settings is not obvious, and a 'faster' result is only useful if the answer is still right and the speedup is repeatable.
>
> How it works: GCC has optimization levels (-O2, -O3) and many individual flags such as -funroll-loops. The GCC manual itself says unrolling 'may or may not make it run faster', so the benefit depends on the program. Some flags (like -Ofast) can change floating-point results. And timings on a real machine vary from run to run, so one measurement proves little.
>
> Relation to NOVA: these three questions (which flags, still correct, speedup real) are exactly what SmartPass tries to handle for a narrow case.
>
> Likely question: 'Do developers really struggle with this?' Honest answer: we did not run a survey. The sources show the configuration space and the measurement problems exist; they do not tell us how common the struggle is.

All stages shown are implemented. No machine-code backend: programs run on the AST and TAC interpreters.

| Stage | What it does and why it matters |
|---|---|
| Lexer | Splits text into tokens (keyword, identifier, integer, operator) with line:column for error messages. |
| Parser | Recursive descent, one function per precedence level; reports the first syntax error with its location. |
| AST | Tree of the program (Let, Print, Binary…), independent of how the text was laid out. |
| Semantic analysis | Symbol table: rejects use of an undeclared variable and duplicate declarations. |
| TAC | Each instruction has at most one operator, e.g. $t1 = x * 2: simple enough to analyze and optimize. |
| Optimizer | Four passes repeated until nothing changes (a fixed point); see slide 10. |
| Interpreter | Runs the AST or the TAC; division by zero is a runtime error with a location. |

NOVA Script: integers only (64-bit wrapping), let, assignment, print, + - * /, parentheses; no loops or branches yet.

**Sources:** docs/language.md; docs/grammar.md; src/*.cpp; include/nova/tac.hpp; docs/DEMO.md

**Speaker notes:**

> In everyday language: the compiler reads a small program, understands its structure, turns it into very simple step-by-step instructions, cleans those up, and runs them.
>
> How it works: the lexer produces tokens with line and column. The parser is recursive descent: one function per precedence level (additive, term, unary, primary), which gives correct precedence for * and / over + and -. The AST records the meaning. Semantic analysis uses a symbol table to reject undeclared and duplicate variables. TAC breaks every expression into instructions with at most one operator, for example $t1 = x * 2; that is easier to analyze than a tree. The optimizer rewrites TAC. The interpreters execute the AST or the TAC.
>
> Relation to NOVA: every stage in the diagram exists in the source (src/lexer.cpp, parser.cpp, semantic.cpp, tac.cpp, optimizer.cpp, interp.cpp). There is no machine-code generator; programs run on the interpreters.
>
> Likely question: 'Where is code generation?' We did not build one. The language is tiny (integers, let, assignment, print, + - * /), so the goal was front end, IR and optimization, not a native backend.

## Slide 5: How NOVA SmartPass Chooses Compiler Flags

1 Examine the workload

2 Select a candidate

3 Compile with GCC

4 Check correctness

5 Measure

6 Record evidence

Repeat until the search budget is used (demonstration setting: at most 4 searched candidates).

Five signals used to choose the next candidate, and their real status

1  Source-code features
Per-kernel facts (size n, working set, streaming?, reduction?) registered for matmul, vector_add, stencil. Not parsed from arbitrary C++.
Used

2  Loop depth
How deeply the kernel's loops nest (recorded: matmul 3, stencil 2). Deeper does not mean faster.
Recorded, not scored

3  Arithmetic intensity
FLOPs ÷ bytes moved, estimated from the kernel definition and n.
Recorded, not scored

4  Memory-bandwidth demand
Proxy only: working set above 4 MiB favors prefetch flags. No bandwidth model, no hardware counters.
Proxy used

5  Historical evidence
Earlier log-gains vs -O2; closer input sizes count more. Needs a history file.
Used if file given

Teaching example for signal 2: two nested loop levels

for (int i = 0; i < n; i++) {
for (int j = 0; j < n; j++) {
result[i] += a[i][j] * x[j];
}
}

Score used today = prior (streaming, reduction, working set > 4 MiB) + history + pilot feedback. A hand-written heuristic, not machine learning.
Loop depth and FLOPs/byte are recorded for explanation; they do not change the order yet.

**Sources:** src/tune/features.cpp, include/nova/tune/features.hpp; src/tune/adaptive.cpp; docs/adaptive.md; src/tune/cli.cpp (tune_usage)

**Speaker notes:**

> In everyday language: SmartPass cannot try every flag combination, so it tries a few, chosen with some care, and keeps a record. Each try is called a candidate: one flag combination from a fixed list. For the demonstration we allow at most four searched candidates (the budget).
>
> The loop in the top row is the same for every candidate: examine the workload, select a candidate, compile with GCC, check correctness, measure, record evidence.
>
> The five signals, and what is REALLY implemented (be exact in the viva):
> 1. Source-code features: the features (size n, working-set bytes, streaming or not, reduction or not) are written per benchmark in src/tune/features.cpp and computed from the benchmark definition and n. NOVA does not read or understand arbitrary C++ source.
> 2. Loop depth: recorded in the features (matmul 3, vector_add 2, stencil 2) but NOT used in the current scoring. Example for teaching: a matrix-vector loop has two nested levels (i outer, j inner). Deeper nesting does not mean faster code; it only describes the structure.
> 3. Arithmetic intensity = floating-point operations divided by bytes moved. NOVA computes an estimate (flops_per_byte) from the kernel definition and n, and records it. It is not used in the current scoring.
> 4. Memory-bandwidth demand: there is no bandwidth model and no hardware counter. The only memory signal used is the working-set size: above 4 MiB the prefetch flag is weighted up. That is an estimate of demand, never a measurement of bandwidth.
> 5. Historical evidence: implemented. A history file (--history=FILE) stores, per benchmark, size and candidate, the log of (O2 median / candidate median) from earlier tuning runs. Similarity: same benchmark counts with weight exp(-|difference in log2 n| / 4); another benchmark counts with weight 0.25. Failures count as a loss of 0.3 in log-gain. History only changes the ORDER in which candidates are tried; it never skips the correctness check. Without a history file the adaptive strategy still runs, using the prior and the pilot feedback.
>
> The score used today is: prior (streaming, reduction, working set above 4 MiB) + history + feedback from the short pilot of already-built candidates. It is a hand-written heuristic, not machine learning.
>
> Likely questions: 'Does it understand my source code?' No. 'Is deeper nesting faster?' No claim. 'Where does bandwidth come in?' Only through the working-set proxy.

**Speaker notes:**

> In everyday language: the budget B is the number of searched candidates SmartPass may build. We demonstrate B = 4. The two baselines, GCC -O2 and -O3, are always built in addition and do not use the budget, so B = 4 means 6 builds.
>
> Selected vs compiled vs valid. In the implementation a candidate is counted the moment it is selected and its build is attempted (src/tune/tuner.cpp: add_candidate increments builds_attempted and evaluations). So 4 selected = 4 compile attempts. How many of those become valid measurements depends on what happens next: a build can fail (BUILD_FAILED), the program can run but give a wrong answer (CORRECTNESS_FAILED), the binary can be rejected by the size policy (REJECTED_BY_POLICY, more than 2.0 times the -O2 binary), or it can be timed and ranked. Failed candidates still count against the budget, and there are no automatic retries. So you get between 0 and 4 valid measured candidates from a budget of 4, never more.
>
> Invalid flags (not in the whitelist, duplicates, or not exactly one -O level) are caught BEFORE anything is built: the run is refused with an error and nothing is counted.
>
> The A to D table is ILLUSTRATIVE. The flag IDs are real members of the 22-candidate space and all four were built in the saved B = 4 runs, but those saved runs used the random strategy. A real adaptive run would choose its own four, ordered by the score from slide 5. Do not say these are adaptive picks, and do not claim any of them is a global optimum: only 22 combinations exist, and the result applies to one machine and one input size.
>
> Likely questions: 'Why does a failed build count?' So random and adaptive search are compared at equal cost, and so a search cannot hide bad luck by retrying. 'Is B fixed at 4?' No: --budget is required and can be 0 to 100000; 4 is the demonstration setting.

Reference (oracle): an independent long-double calculation inside the harness. No reference executable is built.

Anchor = the plain -O2 baseline. Built first and not counted in B. Pilot runs, history log-gains and the binary-size limit (at most 2.0x the -O2 binary) are measured against it.

In the code, candidates are built one by one first (adaptive: with a short pilot against the anchor); validation and timing then run for all built candidates together, interleaved. States: BUILD_FAILED, CORRECTNESS_FAILED, REJECTED_BY_POLICY, ELIGIBLE.

**Sources:** src/bench/harness.cpp (validate_and_time); src/tune/tuner.cpp (anchor, lifecycle states); docs/smartpass.md

**Speaker notes:**

> In everyday language: this is the life of ONE candidate, from being proposed to being ranked. Two things can go wrong, and both are recorded rather than hidden: the build can fail, or the program can build but give a wrong answer.
>
> Stage table (what happens / what is recorded):
> 1 Proposed: the strategy (fixed, random or adaptive) picks the next unevaluated candidate / its flag ID and position in the sequence.
> 2 Budget checked: the search stops when B searched candidates have been used / the evaluation count.
> 3 Compilation attempted: g++ with the fixed flags plus the candidate's whitelisted flags, passed as an argument list, never a shell string / build status, binary size, build log. A failure becomes BUILD_FAILED.
> 4 Correctness validation: one validation run, discarded for timing, is compared with the independent reference / pass or the list of failed checks. A failure becomes CORRECTNESS_FAILED and its timing samples are cleared.
> 5 Performance measurement: 2 warm-up runs, then 15 timed rounds, with all candidates interleaved and the CPU pinned / raw samples, median, IQR.
> 6 Result recorded: manifest.json, results.json/csv, raw_timings.csv, logs.
> 7 Compared: eligible candidates (built, correct, fully timed, binary within 2.0 times the -O2 binary) are ranked by median; rank 1 wins. REJECTED_BY_POLICY marks a too-large binary.
> 8 Next or stop: back to stage 1 while budget remains; otherwise stop and explain.
>
> The anchor is the plain -O2 baseline. It is built first and does not use the budget. Adaptive search compares each new candidate with it in the short pilot, history log-gains are measured against it, and the binary-size limit is relative to it.
>
> Order in the code, for accuracy: first the two baselines and then the searched candidates are BUILT one by one (adaptive: after each build a short pilot of interleaved anchor and candidate rounds, 5 by default, updates the scores). Only after the search ends do validation and the 15-round timing run for all built candidates together, interleaved. The slide shows the lifecycle of one candidate, which is the easiest way to explain it.
>
> Likely question: 'What if the fastest candidate gives a wrong answer?' It is marked CORRECTNESS_FAILED, kept in the record with the reason, and can never be ranked.

## Slide 8: How NOVA Checks That Optimization Has Not Changed the Answer

Five numerical checks (each kernel prints them)

| # | Check | Value compared |
|---|---|---|
| 1 | Total scalar sum | sum = v[0] + … + v[len−1] |
| 2 | First element | s0 = v[0] |
| 3 | Middle element | s1 = v[len / 2] |
| 4 | Final element | s2 = v[len − 1] |
| 5 | Weighted-index checksum | wsum = Σ ((i mod 7) + 1) · v[i] |

Rule (tolerance 1e-9)
|actual − expected| ≤ 1e-9 · max(1, |expected|)
Absolute near zero, relative for large values.

Kernel, n, seed and output length must also match. NaN or infinity fails. No separate empty-output rule: the length must equal the expected length.

Worked example (illustrative values)

| Check | Expected | Candidate | |diff| | Allowed | Result |
|---|---|---|---|---|---|
| sum | 1048.5732 | 1048.5732000004 | 4.0e-10 | 1.05e-6 | Pass |
| s1 | 0.5 | 0.5000000021 | 2.1e-9 | 1.0e-9 | Fail |

One failed check rejects the whole candidate: it is recorded as CORRECTNESS_FAILED and cannot win, even if it is the fastest.

A gate, not a proof
- Five statistics can match while individual elements differ; the project does not compare every element.
- Where practical, a full comparison would be stronger; a scalar-only program would need its own output checks.
- The expected values come from a long-double reference inside the harness, not from a GCC-built executable.

**Sources:** src/bench/registry.cpp; include/nova/bench/registry.hpp (kRelativeTolerance); benchmarks/kernels/common.hpp; src/bench/harness.cpp (tolerance_rule); docs/benchmarks.md

**Speaker notes:**

> In everyday language: after GCC builds a candidate, SmartPass runs it and compares a few numbers from its output with numbers computed independently. If any differ by more than a tiny allowance, the candidate is thrown out, however fast it is.
>
> What is implemented (src/bench/registry.cpp and include/nova/bench/registry.hpp). Every kernel prints five statistics of its output array v of length len: sum (total of all elements), s0 = v[0] (first), s1 = v[len/2] (middle), s2 = v[len-1] (final), and wsum, a weighted checksum: the sum of ((i mod 7) + 1) * v[i]. The weights cycle 1 to 7, so an element moving to another position changes the checksum.
>
> Comparison rule. The tolerance is 1e-9 and it is MIXED, not purely absolute: |actual - expected| <= 1e-9 * max(1, |expected|). For values with |expected| up to 1 that is an absolute tolerance of 1e-9; for large values such as a total of about 1000 it is a relative tolerance, so the allowance grows to about 1e-6. This suits sums of many doubles, where rounding error grows with the magnitude. Please do not say it is purely absolute: the code uses the max(1, |expected|) form.
>
> Other rules. The kernel name, input size n, seed and output length must match exactly. A value that is not a number (NaN) or infinite fails: the parser rejects non-finite output, and the comparison is written as 'not (difference <= limit)', so NaN can never pass. There is no separate rule for empty output: the length must equal the expected length.
>
> Where the expected values come from: a long-double reference computed inside the harness from the kernel's definition and the input seed, independent of any GCC-built binary.
>
> The worked example uses ILLUSTRATIVE numbers, not values from a run: the first pair passes with a difference of 4e-10 against an allowance of about 1e-6; the second fails with a difference of 2.1e-9 against 1e-9.
>
> Limits to say out loud: this is a lightweight gate, not a proof that the optimized program is equivalent. Five statistics of an array can match while individual elements differ, and the project does not compare every element. It was tested with a deliberately wrong kernel, and the -Ofast run (a separate disclosure experiment, V0.6) still passed it on all three kernels, which shows how forgiving the tolerance is. A scalar-only program would need its own outputs to be checked; the current kernels all produce arrays.
>
> Likely question: 'Why not compare all elements?' A full comparison is possible for small outputs and would be a good extension; the current design keeps output cheap and uniform across kernels.

## Slide 9: Faster Code vs. Strict Floating-Point Behavior

What -ffast-math relaxes

- Reassociation: may regroup (a + b) + c as a + (b + c); the rounding differs.
- NaN / infinity: may assume values are never NaN or infinite, so checks like x != x can disappear.
- Signed zero: may treat -0.0 and +0.0 as the same value.
- Reproducibility: the last digits can depend on compiler version, flags and target.

Operation-order example (double precision)

a = 1e16;  b = -1e16;  c = 1.0;
(a + b) + c   ->  1.0
a + (b + c)   ->  0.0   // b + c rounds to -1e16

Why strict rules matter in some fields

- Finance: audited rounding and the same figure on every re-run.
- Aerospace / space: specified, verifiable numerics; NaN and overflow must be detected, not assumed away.
- This does not mean every use of -ffast-math is unsafe; many simulation and graphics programs accept small differences.

In NOVA
- -ffast-math is not in the SmartPass whitelist; such a candidate is refused.
- -Ofast appears only in a separate disclosure run (V0.6) and passed the five checks on all three kernels.
- So the gate cannot show a result is safe for a high-stakes program. Use of fast-math there needs domain-specific validation.

**Sources:** docs/smartpass.md (whitelist, refused flags); docs/benchmarks.md; benchmarks/results/V0.6-ofast-disclosure; state/evidence/V0.6/12_ofast_disclosure_run.log

**Speaker notes:**

> In everyday language: strict floating-point rules make the compiler do the arithmetic in exactly the order you wrote. GCC's -ffast-math (spelled with two f's, not '-fastmath') tells it to relax those rules so it can reorder and simplify the arithmetic, which often makes loops faster, but the last digits of the answer can change.
>
> Reassociation. Real-number addition is associative, floating-point addition is not, because every addition rounds. With a = 1e16, b = -1e16, c = 1.0 in double precision: (a + b) + c = 1.0, but a + (b + c) = 0.0, because b + c rounds back to -1e16 (the spacing of doubles near 1e16 is 2). -ffast-math (through -fassociative-math, part of -funsafe-math-optimizations) allows GCC to pick either order, which also lets it vectorize a sum, since a vector sum adds in a different order.
>
> NaN and infinity. -ffast-math includes -ffinite-math-only: the compiler may assume values are never NaN or infinity, so a test such as x != x (is it NaN?) can be optimized away and an overflow may not be reported.
>
> Signed zero. -fno-signed-zeros lets -0.0 and +0.0 be treated as the same; that matters for functions like 1/x or atan2 that behave differently at -0.0.
>
> Reproducibility. With strict semantics, the same source gives the same bits on any IEEE-conforming build. With fast-math the result can depend on compiler version, flags and target, so two builds of one program can disagree in the last digits.
>
> Why some fields need strict semantics. Financial software must match audited, legally defined rounding and must reproduce the same figure later. Aerospace and space software is verified against specified numerical behaviour and relies on exceptional values (NaN, infinity) being detected, not assumed away. That does NOT mean every use of -ffast-math is unsafe: many graphics, game and simulation codes accept small differences on purpose.
>
> Relation to NOVA. -ffast-math is NOT in the SmartPass whitelist; docs/smartpass.md says a candidate such as '-O2 -ffast-math' is refused with the flag named. The only fast-math-style run is -Ofast in a separate disclosure experiment (V0.6), kept apart from the strict comparisons. In that experiment -Ofast passed the five-check gate on all three kernels. So passing the gate means 'matched within 1e-9 relative on these statistics', not 'safe for a high-stakes program'.
>
> Say clearly: NOVA does not advise using -ffast-math in safety-critical systems without domain-specific validation.
>
> Likely question: 'Can SmartPass choose -ffast-math?' No, it cannot reach GCC unless it is whitelisted.

## Slide 12: What NOVA Adds

Proposed contribution. NOVA SmartPass combines workload-feature-guided candidate selection, a strict four-candidate experimental budget, numerical correctness gating, and recorded evidence to make compiler-configuration tuning more controlled and explainable.

Why each piece helps

- Budget: bounds the experiment; failed builds still count.
- Workload features: decide which candidates are tried first.
- History: helps when a history file is supplied (implemented, optional).
- Numerical validation: rejects results whose answer changed.
- Recorded evidence: explains why a candidate was accepted or rejected (nova explain).

Demonstrated so far (replay study)

**Sources:** report/report.md section 8.2, section 9 (numbers parsed by this script); docs/adaptive.md; src/tune/adaptive.cpp

**Speaker notes:**

> In everyday language: NOVA SmartPass makes compiler-flag tuning more controlled and explainable. It does not make GCC faster by itself.
>
> The five reasons, each tied to something that exists in the code: (1) the budget bounds the experiment: at most B searched candidates plus two baselines, with failures counted; (2) workload features prioritize candidates: the prior favours vectorization and unrolling for streaming loops and prefetching for large working sets, and down-weights vectorization for reductions under strict floating point; (3) history helps when a history file is supplied, otherwise the other two signals still work; (4) numerical validation rejects a candidate whose answer differs, however fast; (5) recorded evidence (flags, raw timings, failures, environment, nova explain) shows why each candidate was accepted or rejected.
>
> Labels to keep straight. 'Proposed contribution' is the design: the combination of those five pieces. 'Demonstrated so far' is only what the measurements show: in the replay study, adaptive search was ahead of random at small budgets by a small margin (B = 4 on holdout sizes: adaptive 1.0xx vs random 1.0xx, values on the chart), the gap shrinks as B grows and everything ties at B = 22, and the individual signals (descriptors, history, feedback) were inconclusive. The study replays saved measurements on one machine with GCC 6.3.0 and three kernels. In real end-to-end runs adaptive spent more tuning time because of its pilot runs.
>
> Likely question: 'What is the benefit in one sentence?' A fixed, small number of tries that are checked for correctness, measured repeatedly, and fully recorded, so a reader can see why a configuration was chosen.

## Slide 14: Limitations, Future Scope and Conclusion

Limitations (documented)

- One machine, old 32-bit GCC 6.3.0; three small kernels.
- Only 22 searchable configurations.
- Timing noise: baseline spread up to 7.2% (median 2.1%).
- Correctness gate: five statistics, not every element.
- Loop depth and arithmetic intensity are recorded but not yet scored; no bandwidth model.
- Adaptive search costs extra tuning time (pilot runs).

Future scope (not implemented)

- Linux and newer GCC; compile and test the POSIX runner.
- Sanitizer runs on a toolchain that supports them.
- More kernels, larger inputs, a bigger flag space.
- Use loop depth and arithmetic intensity in scoring.
- Compare every output element where practical.

Conclusion. NOVA keeps two questions apart: how a compiler works (NOVA Compiler) and how to compare GCC settings carefully (SmartPass). In the measured setting, adaptive search was slightly ahead of random at small budgets; this does not show NOVA is faster than GCC or that results generalize.

**Sources:** report/report.md sections 7, 10, 11; state/KNOWN_ISSUES.md; docs/08-references.md; state/evidence/V0.9/10_references_check.md

**Speaker notes:**

> In everyday language: the results are real but narrow, and the report says so itself.
>
> Limitations, one by one. One machine and an old 32-bit GCC 6.3.0: newer compilers may behave differently. Three small kernels (12 workloads): not representative of real programs. The searchable space has only 22 configurations, so a small budget already covers a lot of it and everything ties at B = 22. Timing noise: baselines had a median spread of 2.1 percent and at most 7.2 percent, so smaller differences are inconclusive. The correctness check uses five output statistics, not every element. ## Slide 15: Glossary

| Term | Meaning in NOVA |
|---|---|
| Workload | A kernel plus its input size, e.g. stencil with n = 200,000. |
| Candidate | One whitelisted flag combination, e.g. O3+unroll+native. |
| Flag | A single GCC option, e.g. -funroll-loops. |
| Binary | The executable GCC builds for one candidate. |
| Budget (B) | Max searched candidates built; the -O2/-O3 baselines are extra. |
| Adaptive search | Next candidate chosen by prior + history + pilot feedback. |
| Accounting rules | Selected and built = counted, even if it fails; no retries. |

| Term | Meaning in NOVA |
|---|---|
| Correctness gate | Five output statistics must match the reference or the candidate cannot win. |
| Tolerance | Allowed gap: 1e-9 · max(1, |expected|) |
| Anchor | The plain -O2 baseline: reference for pilot runs, history and binary size. |
| “Unaccounted anchor” | Not defined in the project. Closest: the uncounted -O2/-O3 anchor baselines. Author to confirm. |
| Arithmetic intensity | Floating-point operations per byte moved. |
| Tuning overhead | Wall-clock time of the whole search (11.49 s in the saved stencil run). |
| Reference | Independent long-double calculation of the expected statistics. |

Definitions follow the code (src/tune/, src/bench/) and docs/smartpass.md; the budget is configurable, 4 is the demonstration setting.

**Sources:** src/tune/*.cpp; src/bench/*.cpp; docs/smartpass.md; docs/NOVA_NotebookLM_Master_Source.md (line 139: 'uncounted anchor baselines')

**Speaker notes:**

> Use this slide to answer 'what do you mean by ...?' in the viva. The definitions follow the code, not a general textbook.
>
> Workload: a kernel plus its input size (stencil, n = 200,000). Candidate: one flag combination from the closed whitelist (-O2, -O3, -funroll-loops, -ftree-vectorize, -fprefetch-loop-arrays, -march=native; exactly one -O level, no duplicates). Flag: one option given to GCC. Binary: the executable GCC produced for one candidate. Budget: the number of searched candidates that may be built; baselines are extra. Adaptive search: next candidate chosen by prior + history + feedback. Accounting rules: every searched candidate that is selected and built counts, including failures; baselines do not; no retries; invalid flags are refused before building. Correctness gate: the five statistics must match the reference within the tolerance. Tolerance: |actual - expected| <= 1e-9 * max(1, |expected|). Arithmetic intensity: floating-point operations per byte moved. Tuning overhead: wall-clock time of the whole search (11.49 s for the saved stencil B = 4 run). Anchor: in the code, the plain -O2 baseline; it is the reference point for the pilot comparison, the history log-gains (log of anchor median over candidate median) and the binary-size limit.
>
> 'Unaccounted anchor' is NOT a term defined anywhere in the project files, code or documents. The closest wording is 'uncounted anchor baselines' in docs/NOVA_NotebookLM_Master_Source.md: the -O2 and -O3 baselines that are always evaluated and not counted against the budget. The slide says so rather than inventing a definition. If your guide or the original brief meant something else by it, the author needs to supply that definition.
>
> Likely question: 'Is the budget counted in builds or in measurements?' Searched candidates built (so failures count); B = 4 means 4 searched builds plus 2 baseline builds.
